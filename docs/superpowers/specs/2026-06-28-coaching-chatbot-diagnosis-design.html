SOMA-152 코칭 챗봇형 진단 설계

작성일: 2026-06-28 · 대상 브랜치: feature/SOMA-152-chatbot-acting-diagnosis

목표

기존 POST /api/v1/coachings는 영상과 배우가 입력한 맥락을 받은 뒤 AI 분석 결과를 즉시 최종 코칭 카드처럼 반환했다. SOMA-152에서는 이 흐름을 챗봇형 진단으로 바꾼다. 첫 요청에서는 최종 평가를 내리지 않고, AI가 영상 기반 초기 컨텍스트와 배우에게 물어볼 질문 하나를 생성한다. 사용자가 그 질문에 답하면 서버는 저장된 초기 컨텍스트와 사용자 답변을 함께 사용해 배우의 의도와 상황을 더 구체화한 최종 진단을 만든다.

결정 사항

  • 상태POST /api/v1/coachings는 COMPLETED가 아니라 QUESTION_READY를 반환한다.
  • 대화첫 응답에는 챗봇에서 물어볼 질문을 하나만 포함한다.
  • 대본대본은 사용자가 별도 입력하지 않고, AI가 영상에서 들리는 대사를 받아쓴 transcript로 둔다.
  • 객관 신호수치화 가능한 객관적 평가는 점수가 아니라 측정 가능한 관찰값으로 둔다.
  • 주관 진단수치화 불가능한 주관적 평가는 확정 평가가 아니라 코치의 진단 가설로 둔다.
  • 최종 진단사용자 답변 후에는 영상을 다시 업로드하지 않고, 저장된 초기 분석 컨텍스트와 사용자 답변만으로 AI를 다시 호출한다.

범위

포함

  • 코칭 상태 QUESTION_READY 추가
  • 초기 챗봇 컨텍스트 응답 DTO 추가
  • 초기 AI 분석 결과 저장 필드 추가
  • 사용자 답변을 받는 최종 진단 API 추가
  • Gemini 프롬프트와 파서 분리 또는 확장
  • 통합 테스트와 AI 파서 단위 테스트 추가

제외

  • 여러 번 이어지는 다중 턴 챗봇 대화
  • 사용자 답변 단계에서 영상 재분석
  • 사용자가 원문 대본을 업로드하거나 입력하는 기능
  • 코칭 결과 조회 API 신설
  • 비동기 작업 큐 도입

사용자 흐름

  1. 사용자가 영상, 장르, 상황, 인물 설정, 선택 서브텍스트를 업로드한다.
  2. 서버는 영상을 저장하고 AI에 초기 분석을 요청한다.
  3. AI는 질문 하나, 영상 대사 transcript, 초기 분석, 측정 가능한 관찰 신호, 진단 가설을 반환한다.
  4. 서버는 코칭을 QUESTION_READY 상태로 저장하고 초기 컨텍스트를 응답한다.
  5. 프론트는 질문을 챗봇 메시지로 보여주고 사용자의 답변을 받는다.
  6. 프론트는 POST /api/v1/coachings/{coachingId}/diagnosis로 답변을 제출한다.
  7. 서버는 저장된 초기 컨텍스트와 사용자 답변으로 AI에 최종 진단을 요청한다.
  8. 서버는 구체화된 상황과 의도, 최종 진단 카드를 저장하고 COMPLETED 상태로 응답한다.

POST/api/v1/coachings

연기 영상을 업로드하고 챗봇 질문을 생성한다. 기존 검증 규칙은 유지한다. 성공 시 HTTP 상태는 기존과 동일하게 201 Created를 사용한다.

요청

필드 타입 필수 설명
video file 예 허용 MIME type은 video/mp4, video/quicktime, video/webm이다.
genre string 예 연극, 영화, 뮤지컬, 드라마, 기타 중 하나다.
customGenre string 조건부 genre=기타일 때 필수다.
situation string 예 배우가 처음 입력한 장면 상황이다.
characterSetting string 예 배우가 처음 입력한 인물 설정이다.
subtext string 아니오 배우가 처음 입력한 서브텍스트다. 비어 있으면 null로 정규화한다.

POST/api/v1/coachings/{coachingId}/diagnosis

챗봇 질문에 대한 사용자 답변을 받아 최종 진단을 생성한다. 이 단계에서는 영상을 다시 업로드하거나 다시 분석하지 않는다.

요청

{
  "answer": "상대가 나를 약하게 볼까 봐 미련을 숨기고 싶었어요."
}
필드 타입 필수 검증
answer string 예 앞뒤 공백 제거 후 비어 있으면 INVALID_DIAGNOSIS_REQUEST로 거부한다.

도메인 모델

기존 Coaching 엔티티는 코칭 요청, 영상 저장 정보, AI 메타데이터, 최종 피드백 카드를 함께 가진다. 이번 변경에서는 초기 분석 컨텍스트와 사용자 답변 기반 구체화 값을 같은 코칭 생명주기에 추가한다.

상태 의미 허용 동작
ANALYZING 영상 저장 또는 초기 AI 분석 중 내부 처리만 허용
QUESTION_READY 초기 분석과 챗봇 질문 생성 완료 사용자 답변 제출 가능
COMPLETED 사용자 답변을 반영한 최종 진단 완료 평가 등록 가능
FAILED 영상 저장, 초기 분석, 최종 진단 중 실패 추가 처리 불가

DB 변경

PostgreSQL과 테스트 DB 마이그레이션을 모두 추가한다. 객관 신호는 구조가 바뀔 가능성이 있으므로 JSON 문자열로 저장하고, API 응답에서는 타입 있는 DTO로 변환한다.

컬럼 타입 설명
initial_question text 챗봇이 사용자에게 물어볼 질문 하나
initial_transcript text AI가 영상에서 받아쓴 대사
initial_analysis text 영상 기반 초기 분석 요약
initial_measurable_signals_json text 측정 가능한 관찰 신호 배열의 JSON 문자열
initial_diagnostic_hypothesis text 코치의 진단 가설
user_answer text 챗봇 질문에 대한 사용자 답변
refined_situation text 초기 입력과 사용자 답변을 함께 반영해 구체화한 상황
refined_intent text 초기 입력과 사용자 답변을 함께 반영해 구체화한 연기 의도

AI 계약

초기 분석 응답

초기 분석 프롬프트는 최종 평가 카드 대신 챗봇 질문과 컨텍스트를 반환하도록 바꾼다. 출력은 JSON 객체 하나로 제한하고, 서버 파서는 필수 필드를 검증한다. 

{
  "question": "string",
  "transcript": "string",
  "analysis": "string",
  "measurableSignals": [
    {
      "name": "pauseCount",
      "value": 3,
      "unit": "count",
      "evidence": "string"
    }
  ],
  "diagnosticHypothesis": "string"
}

최종 진단 응답

최종 진단 프롬프트는 영상 파일 없이 아래 컨텍스트를 전달한다.

  • 사용자가 처음 입력한 genre, situation, characterSetting, subtext
  • 초기 분석의 question, transcript, analysis, measurableSignals, diagnosticHypothesis
  • 사용자 답변 answer

응답은 구체화된 맥락과 기존 피드백 카드 구조를 함께 반환한다. 

{
  "refinedSituation": "string",
  "refinedIntent": "string",
  "feedback": {
    "overallStrength": {
      "text": "string"
    },
    "feedbackCards": [
      {
        "order": 1,
        "title": "string",
        "observations": [
          {
            "timecode": "string",
            "text": "string"
          }
        ],
        "cause": "string",
        "practiceSteps": ["string"],
        "expectedEffect": "string"
      }
    ]
  }
}

애플리케이션 구조

영역 변경
Controller POST /api/v1/coachings 응답 DTO를 초기 챗봇 응답으로 변경하고, POST /api/v1/coachings/{coachingId}/diagnosis를 추가한다.
Service 기존 create는 초기 분석까지만 수행한다. 새 진단 서비스 메서드는 코칭 조회, 상태 검증, 답변 검증, 최종 AI 호출, 완료 저장을 담당한다.
Port CoachingAnalyzer를 초기 분석과 최종 진단을 모두 표현할 수 있게 확장하거나, CoachingDiagnosisGenerator 같은 별도 포트를 둔다. 구현 단계에서는 변경 범위가 작은 쪽을 선택한다.
Domain Coaching에 markQuestionReady, completeDiagnosis 같은 상태 전이 메서드를 추가한다.
Infrastructure Gemini 구현은 초기 분석 프롬프트와 최종 진단 프롬프트를 분리하고, 각각 별도 JSON 파서를 가진다.
Persistence 새 컬럼을 엔티티에 매핑하고 마이그레이션을 추가한다.

오류 처리

상황 HTTP 코드
답변 본문이 없거나 answer가 비어 있음 400 INVALID_DIAGNOSIS_REQUEST
존재하지 않는 코칭 ID 404 COACHING_NOT_FOUND
QUESTION_READY가 아닌 코칭에 답변 제출 409 COACHING_NOT_READY_FOR_DIAGNOSIS
초기 AI 분석 실패 기존 정책 유지 AI_ANALYSIS_FAILED 또는 AI_ANALYSIS_TIMEOUT
최종 진단 AI 실패 500 AI_DIAGNOSIS_FAILED 또는 AI_DIAGNOSIS_TIMEOUT

  • CoachingApiIntegrationTest: POST /api/v1/coachings/{coachingId}/diagnosis가 사용자 답변을 받아 COMPLETED와 최종 진단을 반환하는지 검증한다.
  • CoachingApiIntegrationTest: 빈 답변, 존재하지 않는 코칭, 잘못된 상태의 코칭에 대한 오류 응답을 검증한다.
  • CoachingTests: QUESTION_READY와 COMPLETED 상태 전이가 도메인 규칙을 지키는지 검증한다.
  • GeminiCoachingAnalyzerTests: 초기 분석 JSON 필수 필드와 최종 진단 JSON 필수 필드 누락 시 실패하는지 검증한다.
  • 전체 변경 후 ./gradlew test를 실행한다.

호환성 영향

이 변경은 POST /api/v1/coachings의 성공 응답 의미를 바꾸는 계약 변경이다. 기존 클라이언트가 첫 응답에서 result와 COMPLETED를 기대한다면 프론트 변경이 필요하다.

  • 요청 필드는 유지하므로 업로드 폼 입력 계약은 깨지지 않는다.
  • 성공 응답의 status와 본문 구조는 바뀐다.
  • 최종 결과가 필요한 클라이언트는 새 /diagnosis API를 추가 호출해야 한다.
  • 기존 평가 등록 API는 COMPLETED 이후에만 사용할 수 있도록 유지한다.

구현 순서 초안

  1. 실패하는 통합 테스트로 새 API 계약을 먼저 고정한다.
  2. 초기 컨텍스트와 최종 진단용 DTO, application model을 추가한다.
  3. 도메인 상태와 상태 전이 메서드를 추가한다.
  4. 마이그레이션과 엔티티 매핑을 추가한다.
  5. stub analyzer를 새 계약에 맞춰 수정해 API 테스트를 통과시킨다.
  6. Gemini 프롬프트와 파서를 새 계약에 맞춰 수정한다.
  7. 문서와 기존 API 명세를 실제 구현 결과에 맞게 갱신한다.

구현 기준

  • 초기 컨텍스트 필드명은 응답 예시의 dialogue.question과 context 하위 필드를 그대로 사용한다.
  • measurableSignals.value는 숫자 전용으로 둔다. 숫자로 표현할 수 없는 내용은 evidence에 문장으로 넣는다.
  • 최종 진단 API 응답의 result는 기존 CoachFeedback 카드 구조를 유지한다.
  • AI가 transcript를 만들 수 없는 경우 transcript는 빈 문자열을 허용한다. 단, analysis, question, diagnosticHypothesis는 필수다.
